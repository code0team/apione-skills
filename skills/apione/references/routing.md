# 渠道接入与评估

2026-11-07 源码契约补充见 [接入契约](api-contracts.md)：当前资格需要同路由/同身份匹配的文本、streaming 和 usage，人工停用与自动探测分开；旧测试次数与等级是历史工作口径。静态厂商能力不能凭单个渠道交付样本猜窄，渠道参数必须核对实际交付结果。

## 接入流程

1. 收集提供商别名、API 地址、支持协议和模型列表；凭据从团队受控渠道获取，文档只写字段名或占位符。
2. 使用对应模型族模板，明确填写模型支持列表；已有提供商在编辑页修改。不能因为协议兼容而给所有模型族挂上该提供商。
3. 开启实际需要的文本、图像等能力；同一提供商同时支持文本与图像时需都开启。
4. 配置目标项目/分组的路由及协议车道；网页使用 Web 专用项目，API 使用用户选择的档位。
5. 真实测试模型和所需能力，保存后重新进入核对列表、价格和路由。再建立对账映射。

来源：2026-10-20 16:30–16:34 模板及支持列表修复；10-30 17:40–17:41 直接测试逻辑修复及多能力开关说明。10-30 17:03 曾要求先挂路由再测试，17:40 明确修复为可直接测试，不再把旧前置条件当成强制要求。

## 测试口径

- 10-07 10:26、21:09–21:14：同一简单真实任务，常用且仍受服务的模型至少 5 个，每个测 5 次，并跨时段复测。提供商不足 5 个支持模型时如实列出覆盖缺口，不用不存在的模型凑数。
- 同时记录首字延迟、输出速度、总耗时、成功率和失败原因；能力测试包含工具、思考、视觉、搜索以及真实多轮任务，不以一次 curl 通断代替。
- 10-07 21:07、10-12 09:31–09:42：余额不足、模型下架、搜索声明不兼容和偶发波动要分开。补余额后可复测，不能把其中一个模型或一次错误判成整家永久不可用。
- 10-15 15:25：历史可用率分级为 A ≥90%、B ≥80%、C ≥70%、D ≥60%，低于 60% 异常。这是当时分级展示口径，不是自动上架标准，也不等于综合评分算法。
- 10-03 13:25 的首字超过 8 秒筛选要求是早期文本渠道标准，不能套用图片、视频总生成时长。
- 10-28 23:21–23:24：资格探测按上游的工具、思考、视觉等能力筛选可用渠道；探测通过不保证长期稳定。

## 路由判断

10-19 14:05：分组可绑定路由策略，例如健康优先；权重、当前策略和探测间隔以实际后台为准。10-23 18:07 曾修复跨项目健康证据不可见及单次超时淘汰整条渠道的问题，避免把一次失败直接当永久淘汰依据。

10-23 20:02：只有一个可用提供商时无法故障切换。多提供商全部拒绝时轮询也不能创造可用资源。不要通过跨 API 档位来兜底。

11-02 12:12–14:27：曾出现真实余额耗尽，也出现历史 429/负额度告警后人工复测恢复的情况。核对账户余额、具体模型/车道、请求时段和最新复测，再决定充值、降权或排查配额，不能只凭一条旧告警下结论。
